### 5. NEXT-chip freeze (signal storm bug fix — kept)

Root cause: my own Phase 2 work. I added `queue_changed.emit()`
inside `pick_next_item` to drive Studio's refresh. But `peek_next`
calls `pick_next_item` 5 times internally (simulated, cursor
restored). Each simulated call emitted `queue_changed` →
Studio's handler re-called `peek_next` → 5 more emits → cascade.

**Fix:** `_suppress_queue_emit` flag on scheduler. `peek_next` sets
True before simulation, restores after. Real commits emit; peek
doesn't.

### 6. Random song re-shuffle every second (root-cause fix — kept)

After the signal-storm fix, operator noticed: queue panel showed
different songs every second.

**Root cause:** Scheduler's own docstring (engine.py:612-615)
explicitly warns:
> "Per-type pickers do random.choice over candidate sets. Repeating
> peek_next may return different song picks for random_from_category
> slots — the CURSOR sequence is deterministic, the song identity
> is not."

My Phase 2 `_on_tick` called `_load_upcoming_queue` every 1Hz → 5
fresh `random.choice` picks → queue shuffled every second.

**Fix:** `_check_upcoming_dispatches` now returns bool (preview
lists changed?). `_on_tick`:
- If changed → `_load_upcoming_queue` (full rebuild, OK to re-pick)
- If not → `_refresh_upcoming_panel` (re-render cached, no peek)

Real cursor advances still trigger fresh peeks via `queue_changed`
signal (scheduler emits on real commit).

## NIGHT_LOG carry-overs + this session's lessons

Carry-over incidents 1-24 unchanged from previous handovers. This
session adds:

### Incident #25 — Music-to-spot fade architecture mismatch
**Symptom:** Operator's "spot overlay on music sounds bad"
complaint persisted through 4+ iterations of fade-tweaking.
**Root cause:** I was iterating in the wrong dimension. Music-to-
music crossfade SHOULD overlap (musical bleed). Music-to-spot
should NOT overlap (clean voice). The fix isn't to tune the overlap
ramp — it's to DEFER the music fade entirely when SOTG/Spot is
pending, let music play to natural EOS, then spot fires on a deck
that's truly silent.
**Lesson:** When operator says "still same issue" through multiple
fix iterations, step back and check whether the OVERALL APPROACH
is correct, not just the parameters. The defer pattern was a
fundamentally different architecture; the previous ramp variants
were all parameter-tuning the wrong model.

### Incident #26 — Phase 5 BASSmix retry blocked
**Symptom:** With `route_via_mixer=True`, every audio playback
stuttered ("atak atak") + pause didn't audibly silence.
**Tried + didn't fix:** rate match, decode-flag-Play skip, Mixer
ChannelFlags pause, MIXTIME sync modifier, Mixer_ChannelGetPosition
for position polling, CHAN_BUFFER flag (ChatGPT advice), slide-then
pause pattern.
**Root cause:** Unknown. Operator deferred. Possibilities:
- Multi-engine device contention (other engines still direct-play
  while AudioEngine mixer-routed)
- Hidden BASS config (BASS_CONFIG_BUFFER, BASS_DEVICE_LATENCY
  flag at init, etc.)
- Sample-clock skew at low level we can't see from Python
- Operator's specific Windows audio driver layer
**Lesson:** The migration plan was correct in shape (opt-in flag,
gradual engine-by-engine, rollback-safe), but the underlying
BASSmix integration needs deeper isolation testing BEFORE attempt-

The diagnostic script at `scripts/diag_mixer_stutter.py` runs 5

### Incident #27 — Random song re-shuffle from 1Hz tick
**Symptom:** Operator: "playlist queue mai songs automatically
changes ho rahe hai, fix nahi hai queue."
**Root cause:** Scheduler's `peek_next` calls `pick_next_item` 5
times internally; each `pick_next_item` for a `random_from_category`
slot does a fresh `random.choice` over the candidate set. The
scheduler's docstring explicitly warns about this — "the CURSOR
sequence is deterministic, the song identity is not." My Phase 2
1Hz tick rebuild was calling `peek_next` every second, causing
visible song shuffling.
**Fix:** `_check_upcoming_dispatches` returns bool (preview lists
changed?). `_on_tick` only triggers full rebuild on real changes;
otherwise re-renders cached preview with fresh time-stamps.
**Lesson:** Read the docstrings carefully — the scheduler self-
documents non-determinism. Our refresh frequency must respect that.

### Incident #28 — Signal storm in peek_next
**Symptom:** NEXT-chip frozen, queue panel sluggish.
**Root cause:** I added `queue_changed.emit()` inside
`pick_next_item`. `peek_next` calls it 5x internally. Each emit
hit Studio's handler which called `_load_upcoming_queue` which
called `peek_next` again → exponential signal cascade.
**Fix:** `_suppress_queue_emit` flag on scheduler. `peek_next`
sets True during simulation; only real commits emit.
**Lesson:** Any signal emitted inside a method that's also called
non-destructively by a SIMULATION path needs explicit gating.
