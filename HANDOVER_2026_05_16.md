## NIGHT_LOG carry-overs + this session's lessons

(Carry-over incidents 1-20 unchanged from `HANDOVER_2026_05_15.md`
and `HANDOVER_2026_05_14_v2.md`. This session adds 4 incidents.)

### Incident #21 — main.py crash on Windows Explorer launch (PyInstaller console=False)

**Symptom:** Double-clicking the installed `.exe` from File
Explorer popped a Windows error dialog: "Failed to execute script
'main' due to unhandled exception: 'NoneType' object has no
attribute 'buffer'" — referencing `main.py:23`.

**Root cause:** PyInstaller's `console=False` build runs the app
as a Windows GUI process, NOT attached to a console. Therefore
`sys.stdout` and `sys.stderr` are both `None`. The startup code at
line 21-24 tried to wrap them in UTF-8 TextIOWrappers via
`.buffer` access, which crashed.

**Fix:** Guard with `if sys.stdout is not None and hasattr(sys.stdout, "buffer")`
before wrapping. Same for stderr. Now the wrap only fires when an
interactive console is actually attached (dev mode via
`py main.py`).

**Lesson:** ANY environment-dependent attribute access at module
import time needs defensive guards before PyInstaller packaging.
Test the .exe from Windows Explorer (NOT from bash/cmd which DO
attach stdout) before declaring a build done.

### Incident #22 — premium dialog appearing off-screen / behind window

**Symptom:** Operator clicked "Delete Selected Clock" in Main
Auto Schedule — nothing visible happened. Button looked broken.

**Root cause:** `_PremiumDialog.__init__` in `core/dialogs.py`
positioned the dialog by reading `parent.geometry()`. `geometry()`
on a QWidget returns coords IN THE PARENT'S COORDINATE SYSTEM, NOT
screen coords. For nested widgets (AutoSchedule mounted in
MainWindow's stack), parent.geometry() = (0, 0, 1338, 691) is
*local to the stack*. The dialog called `self.move(669-230, 345-120)`
= `self.move(439, 225)` interpreted as SCREEN coords — which could
land off-screen if MainWindow was positioned far right, or behind
another window. `dlg.exec()` then blocks indefinitely waiting for
an invisible dialog to be dismissed.

**Fix:** Walk up via `parent.window()` to the top-level QMainWindow,
use `frameGeometry()` (screen coords), centre the dialog there.
Fallback chain to QApplication.primaryScreen().availableGeometry()
and finally hard-coded (480, 360).

**Lesson:** When positioning top-level (frameless) widgets,
**always use screen coordinates**. The conversion is `parent.mapToGlobal(parent.rect().center())`
or via `parent.window().frameGeometry()`. Widget-local
`geometry()` interpreted as screen coords is a silent bug.

### Incident #23 — delete_clock FK cascade failure on real clocks

**Symptom:** Even after fixing Incident #22 (dialog appears now),
operator clicked Delete on "E2E Pipeline Test" — dialog showed,
confirmed, log warned "delete_clock failed: FOREIGN KEY constraint
failed". Test 01 (no broadcast history) deleted fine. E2E Pipeline
Test (3 clock_slots, 109 broadcast_log rows) failed.

**Root cause:** `db.delete_clock` previously just did
`DELETE FROM clocks WHERE id = ?`, relying on schema-declared
ON DELETE CASCADE on the child tables. But the live dev DB was
created from an OLDER schema version where those cascades weren't
declared. `auto_schedule.py:_delete_clock_with_cells` had a partial
workaround for auto_schedule rows but missed clock_slots and
broadcast_log.

**Fix:** Manual cascade inside `db.delete_clock`:
- DELETE clock_slots (slots are owned)
- DELETE auto_schedule (grid cells, gone with clock)
- DELETE ai_rotation_decisions (try/except for back-compat)
- UPDATE broadcast_log SET clock_id = NULL (preserve history)
- UPDATE force_clocks SET clock_id = NULL (preserve override row)
- DELETE clocks WHERE id = cid
All in a single transaction with rollback on failure.

**Lesson:** When a DB's structural integrity depends on FK
cascades, **don't trust the schema** — verify the live DB's
actual constraint state, or implement explicit manual cascade
to be safe across schema versions. Also: **preserve historical
references via NULL-out rather than DELETE** when the row carries
audit-trail value (broadcast_log = playback history; we don't
want to lose 109 records of what aired just because a clock was
deleted).

### Incident #24 — desktop shortcut showing generic blank icon

**Symptom:** After install, the desktop shortcut showed a generic
Windows blank-file icon instead of the RA logo. (Start Menu
shortcut had the same problem briefly during the early Phase N
work.)

**Root cause:** The Inno Setup `IconFilename` parameter on the
shortcut points to `{app}\assets\icon.ico` — a filesystem path
that Windows resolves at shortcut-display time. This is flaky:
- Stale Windows icon cache shows the previous (broken) icon
- UAC-protected Program Files folder sometimes can't be read
- Filesystem-path icons aren't recognised as "the official" icon

**Fix:** Removed `IconFilename` from both shortcut entries. Without
it, Windows extracts the icon directly from the .exe (PyInstaller
already embedded the multi-res icon via `icon='assets/icon.ico'`).
Single source of truth: the .exe binary. Same icon shows in
Explorer, taskbar, Alt-Tab, shortcuts, everywhere.

**Lesson:** For Windows shortcut icons, **rely on the .exe's
embedded icon resource**, never filesystem-pointed `IconFilename`
paths. This is what Adobe / Spotify / Discord / every professional
app does.

- **Packaging discipline** — never use `optimize=2` with code
  that relies on docstrings or `assert` for runtime checks. We
  audited and the codebase is fine, but future contributors
  need to know.
- **Path resolution always via `core.paths.resource_path`** —
  no more hardcoded `os.path.join(_HERE, "assets", …)` patterns.

  PyInstaller-frozen .exe from Windows Explorer (NOT from a
  terminal) before declaring distribution-ready. The stdout=None
